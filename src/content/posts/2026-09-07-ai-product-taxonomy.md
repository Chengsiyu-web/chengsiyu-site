之前一直试图通过和 AI 不断交互发问来得到一个大而全的分类体系，维度越写越多，却发现对这些 AI 应用本身的理解越来越糊涂。这次换一个使用者单纯的视角，从两个点来拆分这些工具：**"我能做什么"（参与度/专业能力）+ "我要什么"（交付物）**，以及一些体验感的问题。

AI 编码工具先按"能不能执行"分成两半。

## 一、对话助手（CHAT 形态）

![对话形态与执行形态的对照](/images/posts/ai-taxonomy.svg)

ChatGPT、Claude、DeepSeek、Kimi、豆包。

这类产品形态高度相似，护城河在于聊天框背后的能力：

- **模型能力壁垒：谁更聪明。**能不能准确理解复杂问题、回答是否可靠、长文代码图片等任务能不能处理、响应速度和使用成本如何。
- **数据与反馈壁垒：谁越用越懂用户。**大量用户每天产生真实问题、修改意见、点赞点踩和连续对话，这些数据可以帮助产品发现：用户最常问什么、哪些回答看似正确但实际不好用、哪些任务需要补工具改模型或优化交互。因此，用户越多，反馈越多，产品就可能迭代得越快，形成"更多用户 → 更多数据 → 更好体验 → 更多用户"的循环。
- **用户心智：有问题先想到谁。**Chat 工具功能很像，用户通常不会同时深度使用很多个，因此"遇到问题先打开哪个产品"非常重要。
- **用户迁移成本：换工具会不会损失东西。**随着用户持续使用，产品里会逐渐积累历史对话和个人偏好、自定义助手、Prompt、知识库、文件和项目上下文，以及与办公软件、代码工具及第三方服务的连接。积累越多，迁移成本越高。用户换一个产品，不只是换聊天框，而是要重新教它"我是谁、我在做什么、我习惯怎么工作"。

<summary>Case 积累：豆包如何成为国民级 Chat AI 工具</summary>

**1. 拉新：用字节的流量能力迅速完成全民教育。**豆包背后有抖音、今日头条等庞大的用户入口，也有字节成熟的投放、推荐和品牌营销能力。它解决的不是让已经懂 AI 的人换工具，而是让原本不用 AI 的大众第一次开始用 AI。豆包更像消费 App 打法：反复曝光、降低认知成本，让"有问题问豆包"成为大众心智。

**2. 激活：不强调技术，而是把 AI 包装成普通人会用的产品。**豆包的名字、界面和交互都比较生活化，不要求用户理解模型、Prompt、Token。同时，它不只提供文字问答，还把语音对话、拍照识别、图片生成、搜索、写作等能力放进一个入口。用户不需要先想"该使用哪种 AI 能力"，只需像聊天一样提出需求。这使它更适合下沉到非技术用户、学生、老人等更广泛人群。

**3. 转化：长期免费，把尝试成本压到最低。**早期多数普通用户并没有强烈的 AI 付费意愿。豆包依靠字节的资金、算力和模型成本能力，长期提供低门槛免费服务，相当于用投入换市场教育和用户规模。用户面对的是：不需要科学上网、不需要学习复杂操作、不需要先付费、下载后马上能用。从"听说过 AI"到"真正用一次 AI"的转化链路很短。

**4. 留存：用多场景覆盖，而不是只押注专业能力。**ChatGPT、Claude 早期更容易吸引程序员、知识工作者等专业用户；豆包覆盖的则是更日常的需求：问生活问题、陪聊和语音对话、修图、生成图片、写文案、搜索信息。单个场景未必特别强，但多个低门槛场景叠加，让普通用户更容易找到一个持续使用的理由。

所以，豆包真正的增长公式是：**字节流量触达 × 免费降低门槛 × 大众化产品包装 × 多场景留存 × 快速迭代。**

**Chat 的天花板在哪？**Chat 工具是信息顾问。最大的局限是任务完成的结果太单一，挤牙膏式的用户问答——**适合回答问题，不天然适合完成任务。"告诉用户怎么做"不等于"把事情做完"。**

例如用户说"帮我整理竞品数据"，普通 Chat 可能给出调研方法和表格模板，但真正完成任务还需要：把任务定义和流程设计的责任交给了用户（完成质量取决于用户的输入）；输出通常停留在文字层，离真实结果还有一段距离（只给建议/信息，没有执行交付能力）；擅长一次性交互，但不天然具备项目、状态和流程管理能力（说完就忘）。

总结：**高通用性，但低确定性；擅长交流，但不天然擅长稳定地完成复杂任务。**因此，Chat 可能不会消失，但会从产品的全部逐渐变成一个**交互入口**：用户通过聊天表达目标，背后由记忆、知识库、Workflow、Agent 和各种工具负责规划、执行与验证。从产品演进上看，可以理解为 **Chat 解决"我可以问 AI 什么"，Agent 进一步解决"AI 能不能替我把事情做完"。**

## 二、Agentic：AI 开始直接作用于工作环境

### 两种典型工作环境：IDE 与 CLI

相同的 Agent 能力既可以运行在终端中，也可以被嵌入 IDE。真正发生变化的是：**用户通过什么方式观察 Agent、给 Agent 提供信息，以及在什么时点介入任务。**

**IDE：写 + 看 diff + 随手改，以"共同编辑"为中心。**公开市场主流包括 Cursor、Windsurf、VS Code + Copilot、JetBrains Junie、Trae、通义灵码等。IDE 的屏幕是一块同时铺开的空间：中间是你正在写的代码，左边文件树，右侧 AI 对话，diff 直接标在代码行上（红绿高亮）。所有信息按位置组织，你的眼睛可以在任意两处之间自由跳——扫一眼文件树知道项目多大，看一眼高亮知道改了哪几行。你消费信息的方式是扫视。因此，IDE 更适合**扫视、比较和局部定位**。

**CLI（终端命令行）：以"任务执行"为中心。**CLI 的信息则主要沿时间向前展开。Agent 搜索了什么、读取了哪些文件、执行了什么命令、发现了什么错误，通常会依次出现在文本流中。用户看到的是一段任务过程：先搜索相关代码 → 找到入口 → 修改文件 → 执行测试 → 根据报错继续修复。因此，CLI 更适合**跟踪过程和理解任务进展**。

### Harness：决定 Agent 表现的运行时框架

上面的环境差异，只解释了用户为什么会感觉不同，还没有解释 Agent 为什么会表现不同。真正决定 Agent 具体行为的是环境下面的 Harness。**IDE 与 CLI 决定用户站在哪里观察和介入，Harness 决定 Agent 在这个环境里如何工作。**

"Harness"（运行时框架）是包在模型外面的那层执行系统——它决定工具怎么被调用、输出怎么呈现、上下文怎么管理。不同 Harness 用同一个模型，体验差别可以很大。它是决定这个 Agent 好不好用的核心。

用最直观的体会来说，使用 Agent 时你可能发现：

- 让它跑个删文件的清理命令——有的它问了你 8 次确认，问到你烦；有的配置成全自动，rm -rf 直接下去了，路径写错了也拦不住。
- 跑半小时的大重构——有的中途跑偏了，你只能眼睁睁看着它错下去，或者打断之后整个上下文丢了，重新解释一遍需求；有的可以随时 Esc 打断说"方向不对，是 X 不是 Y"，它带着之前的上下文改道继续；跑太久自动压缩历史，不会聊到一半突然"我们刚才在干什么来着"。
- 第二天的上下文记忆——有的完全失忆，问你"你说的那个项目是什么"，从头解释目录结构、技术栈、你在干嘛；有的有 memory 和 CLAUDE.md 在，它一上来就知道你是谁、在干啥，直接进入正题。

常见的几种模式：Full Auto（给 AI 较完整的工具权限和更长的执行循环，默认不请求批准，除非触发明确禁止项）、Plan Mode（先列计划不执行）、实时确认模式（每次关键动作都先问用户）。

**为什么同一个模型，体感会差这么多？**

| Harness 差异 | 你感受到的区别 |
| --- | --- |
| 循环逻辑 | 回答一次就停，还是会"修改—测试—发现错误—继续修复" |
| 工具集 | 只能写文字，还是能搜代码、改文件、跑终端 |
| 上下文管理 | 只看到你发来的文件，还是会自动找到相关代码 |
| 审批机制 | 每一步都问你，还是只在高风险操作时询问 |
| 权限边界 | 只能给建议，还是能改项目，甚至操作外部系统 |

VS Code 官网说：**"Use the agent harness and models you want"**——VS Code lets you choose the harness and model separately. 你可以选择你已经用过并且觉得好用的 Harness，把他们移植到 VS Code 里跑。如果你在 VS Code 里装 Claude Code 插件，就相当于把原来有一定操作成本的终端入口从终端挪进了侧边栏，拥有了一个更好操作的工作台 + 本身很好的规划/执行能力。

### 一体化还是嵌入式：平台竞争的经典分叉

**一体化路线：壳子与 Harness 共同设计**，以 Cursor 为代表。优势是代码、Diff、对话、终端和 Agent 循环可以深度打通，交互细节由同一家公司统一控制，更容易形成流畅一致的使用体验。代价是需要长期维护编辑器、扩展兼容和开发工具链，用户需要迁移工作环境，产品与特定壳子深度绑定。

**嵌入式路线：Harness 进入用户已有环境**，以 Claude Code 进入终端、VS Code 和 JetBrains 为代表。优势是 Harness 可以跨多个工作环境复用，用户不必放弃已有编辑器，厂商可以把投入集中在模型、Agent 循环和工具能力上。代价是不同宿主中的体验难以完全一致，关键交互受宿主能力限制，Harness 与壳子之间可能存在割裂。

背后各有算盘：模型厂商的主业是卖模型，Harness 是给模型修的高速公路，自造 IDE 反而会把战场拉到自己不占优的领域（编辑器工艺）去硬碰；而编辑器厂商的算盘相反——把 Harness 绑在自己的壳子上，壳子就是它的护城河。选哪条路，取决于你真正的护城河在哪一层。
